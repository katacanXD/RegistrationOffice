**Цель**

Документ описывает стандарты и рекомендации по написанию автоматизированных тестов для backend-репозитория проекта RegistrationOffice.

**Область применения**

Применяется ко всем разработчикам, работающим с кодовой базой `backend/` и создающим unit, integration или E2E тесты.

**Основные принципы**

- Тест должен проверять одно поведение; избегать множественных независимых утверждений.
- Предпочитать малые, быстрые unit-тесты; интеграционные — только для покрытие взаимодействий и контрактов.
- Использовать тестовые данные, понятные человеку (readable fixtures).
- Изолировать внешние интеграции (вызовы сети, файловые операции, внешние БД) в unit-тестах через моки/фейковые реализации.

**Типы тестов и где их размещать**

- Unit-тесты: `src/test/java/...` — Mockito, AssertJ, JUnit 5. Тесты классов сервисов, мапперов, утилит.
- Repository-тесты: `@DataJpaTest` — проверяют SQL-результаты с in-memory H2. Разместить рядом с репозиторием.
- Контроллеры: MockMvc или `@WebMvcTest` для проверки маршрутов, валидации и установки cookies/заголовков.
- Интеграционные тесты: `@SpringBootTest(webEnvironment = RANDOM_PORT)` — для проверки контекстов и основных сценариев.
- E2E (опционально): отдельный pipeline/окружение с реальным БД/сервисами.

**Структура теста (рекомендуемый шаблон)**

1. Arrange — подготовка объектов/моков/данных
2. Act — выполнение проверяемого действия
3. Assert — проверки результатов и взаимодействий

Формат имени: `ClassName_MethodUnderTest_ExpectedBehavior()`
Примеры: `AuthServiceImpl_register_success()`

**Правила использования моков и фикстур**

- Использовать Mockito для мокирования внешних зависимостей; избегать чрезмерного мокирования (не мокать то, что нужно реально проверить).
- Для репозиториев использовать `@DataJpaTest` и сохранять минимальные сущности через репозиторий.
- Общие тестовые утилиты/фабрики размещать в `src/test/java/ru/katacan/registrationoffice/testutil`.

**Покрытие и метрики**

- Минимальный целевой порог покрытия: 70% по backend. Для критичных модулей — 85%.
- JaCoCo используется для отчётов; отчёты генерируются командой `./gradlew jacocoTestReport`.
- Порог покрытия можно выставлять в CI как gate (опционально).

**Интеграция с CI**

- На CI (GitHub Actions и GitVerse) запускать `./gradlew test jacocoTestReport`.
- Сохранять артефакты отчётов (`build/reports/tests`, `build/reports/jacoco/test/html`).
- CI должен прерывать merge/push при падении тестов.

**Запуск локально**

```bash
cd backend
./gradlew test
./gradlew jacocoTestReport
```

**Примеры и шаблоны**

- Unit-тест сервиса: `src/test/java/.../service/AuthServiceImplTest.java` (пример в репозитории).
- Репозиторный тест: `src/test/java/.../repository/DictRoleRepositoryTest.java`.
- Контроллер: `src/test/java/.../controller/AuthControllerTest.java`.

**Рекомендации по PR**

- Каждый новый PR, влияющий на логику, должен сопровождаться соответствующими тестами.
- Маленькие и атомарные тесты предпочительнее большого списка проверок в одном тестовом методе.
- В описании PR указывать краткую сводку новых тестов и ссылки на `TESTS.md` и этот документ.

**Поддержка и помощь**

Обращаться к владельцу модуля (см. `README.md`) или в канал команды QA для согласования покрытия и тестовых сценариев.
