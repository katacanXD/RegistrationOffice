## Процесс 1: Пациент записывается на приём

### Участники (пулы)
- Пациент
- Система RegistrationOffice

### Описание шагов

1. Пользователь входит в систему и попадает в кабинет пациента.
2. Если полис ОМС ещё не привязан, пользователь вводит его и сохраняет.
3. Система разрешает переход к поиску врача только после наличия полиса.
4. Пациент выбирает врача на странице поиска.
5. Система загружает слоты врача на выбранную дату.
6. Если на дату нет слотов, интерфейс ищет ближайший день со свободными слотами в пределах 14 дней.
7. Пациент выбирает время и подтверждает запись в модальном окне.
8. Backend проверяет дату и время, наличие врача и пациента, а также отсутствие конфликта по слоту.
9. При успехе запись создаётся со статусом `booked`.
10. Пользователь возвращается в кабинет пациента со списком обновлённых записей.

### Условия ветвлений

- Если полис не привязан, пользователь не может перейти к поиску врача.
- Если свободных слотов нет, система предлагает выбрать другую дату или другого врача.
- Если слот уже занят, система возвращает ошибку двойного бронирования.

## Процесс 2: Регистратор записывает пациента

### Участники (пулы)
- Регистратор
- Система RegistrationOffice

### Описание шагов

1. Регистратор открывает поиск пациентов.
2. Выбирает пациента и открывает его карточку.
3. Переходит к поиску врача.
4. Выбирает врача и дату записи.
5. Выбирает свободный слот.
6. Подтверждает создание записи для выбранного пациента.
7. Backend создаёт запись через админский endpoint и возвращает результат.

## Процесс 3: Перенос записи

### Участники (пулы)
- Пациент или регистратор
- Система RegistrationOffice

### Описание шагов

1. Пользователь открывает существующую запись.
2. Нажимает «Перенести».
3. Система сохраняет идентификатор переносимой записи и выбранного врача.
4. Пользователь выбирает новую дату и слот.
5. Система вызывает `PATCH /api/v1/appointments/{id}` с новым `slot_datetime`.
6. После успеха пользователь возвращается на соответствующий экран кабинета.

### Условия ветвлений

- Перенос выполняется через тот же календарный экран, что и создание записи.
- При ошибке слота пользователь остаётся на календаре и выбирает другое время.

## Процесс 4: Отмена записи

### Участники (пулы)
- Пациент или регистратор
- Система RegistrationOffice

### Описание шагов

1. Пользователь открывает карточку записи.
2. Нажимает «Удалить».
3. Система запрашивает подтверждение в браузере.
4. При подтверждении вызывается `DELETE /api/v1/appointments/{id}`.
5. Запись переводится в `canceled`.
6. Список записей обновляется.

### Примечание

- Поле причины отмены в текущем UI и API не используется.

---

## Процесс 5: Врач просматривает расписание

### Участники (пулы)
- Врач
- Система RegistrationOffice

### Описание шагов

1. Врач входит в систему и открывает календарь.
2. Система загружает календарь месяца и расписание выбранного дня.
3. В календаре подсвечиваются дни с рабочими слотами и днями с записями.
4. При клике на занятый слот открывается карточка талона с данными пациента.

## Точки принятия решений

| Шлюз                    | Тип  | Описание                                 |
|-------------------------|------|------------------------------------------|
| Полис привязан?         | XOR  | пациент может перейти к поиску врача     |
| Есть свободные слоты?   | XOR  | система предлагает другую дату или врача |
| Слот свободен?          | XOR  | предотвращение двойного бронирования     |
| Это занятый слот врача? | XOR  | открывать ли талон записи                |

## Исключения

- Если пользователь не авторизован, он перенаправляется на страницу входа.
- Если данных нет, экран показывает пустое состояние без ошибок.
- Если backend недоступен, интерфейс показывает текст ошибки загрузки.
