## Общие принципы

- Навигация строится через отдельные страницы и верхний хедер с аватаром; бокового меню нет.
- Для пациента запись доступна только после привязки номера полиса ОМС.
- Все ошибки показываются inline под формой или в виде текста на странице; toast-уведомления в текущем UI не используются.
- Для переноса записи используется тот же календарный экран, что и для создания записи.
- Удаление записи реализовано через подтверждение в `window.confirm`, без поля причины.

## Экран 1: Вход

**Сценарий:** пользователь входит в систему по логину и паролю.

**Состав:**
- поля `login`, `password`;
- кнопка «Войти»;
- ссылка на регистрацию.

**Логика:**
- успешный вход возвращает `access_token` и `user`;
- роль определяет стартовый маршрут:
  - patient → `/patient/main`
  - doctor → `/doctor/calendar`
  - registrar → `/registrar/patients`
  - admin → `/admin`

**API:** `POST /api/v1/auth/login`

---

## Экран 2: Регистрация

**Сценарий:** новый пациент создаёт учётную запись.

**Состав:**
- поля `login`, `lastName`, `firstName`, `middleName`, `password`, `confirmPassword`;
- кнопка «Зарегистрироваться».

**Логика:**
- на backend отправляется `fio` как строка `Фамилия Имя Отчество`;
- после успешной регистрации пользователь возвращается на страницу входа;
- роль при регистрации не выбирается, создаётся пациент.

**API:** `POST /api/v1/auth/registration`

---

## Экран 3: Кабинет пациента

**Маршрут:** `/patient/main`

**Сценарий:** пациент видит полис и свои записи.

**Состав:**
- хедер с логотипом и меню пользователя;
- блок номера полиса ОМС;
- список записей в виде карточек;
- действия для каждой записи: «Удалить», «Перенести».

**Логика:**
- если полиса нет, показывается поле ввода и кнопка «Сохранить»;
- если полис есть, показывается кнопка «Записаться»;
- переход к поиску врача доступен только при наличии полиса;
- перенос записи сохраняет выбранного врача и `rescheduleAppointmentId` в общем контексте.

**API:** `GET /api/v1/patients/me/dashboard`, `PATCH /api/v1/patients/me/policy`, `DELETE /api/v1/appointments/{id}`

---

## Экран 4: Поиск врача

**Маршрут:** `/patient/search`

**Сценарий:** пациент выбирает врача перед записью.

**Состав:**
- поле поиска `Имя / Специалист`;
- карточки врачей с ФИО и специальностью;
- кнопка «Назад».

**Логика:**
- при отсутствии полиса пациент возвращается в кабинет;
- поиск работает по введённой строке;
- клик по карточке сохраняет выбранного врача и ведёт на календарь.

**API:** `GET /api/v1/doctors`

---

## Экран 5: Календарь пациента

**Маршрут:** `/patient/calendar`

**Сценарий:** пациент выбирает дату и свободный слот.

**Состав:**
- календарь месяца;
- список слотов по времени;
- модальное окно подтверждения записи.

**Логика:**
- календарь показывает только доступные даты текущего/следующего выбора;
- если на выбранную дату слотов нет, экран автоматически ищет ближайший день со слотами в пределах 14 дней;
- слоты разделяются на «до 13:00» и «после 13:00»;
- подтверждение закрывает модалку и возвращает пользователя в кабинет.

**API:** `GET /api/v1/doctors/{doctorId}/slots`, `POST /api/v1/appointments/me`, `PATCH /api/v1/appointments/{id}`

---

## Экран 6: Календарь врача

**Маршрут:** `/doctor/calendar`

**Сценарий:** врач просматривает своё расписание и детали записи.

**Состав:**
- календарь месяца;
- список слотов на выбранный день;
- модальное окно с талоном записи.

**Логика:**
- календарь подсвечивает рабочие дни и дни с записями;
- по клику на занятый слот открывается талон с ФИО врача, пациента, полисом и адресом;
- свободные слоты отображаются как `open`, занятые — как `closed`.

**API:** `GET /api/v1/doctors/{doctorId}/calendar`, `GET /api/v1/doctors/{doctorId}/schedule`, `GET /api/v1/appointments/detail/{appointmentId}`

---

## Экран 7: Поиск пациента регистратором

**Маршрут:** `/registrar/patients`

**Сценарий:** регистратор ищет пациента и открывает его карточку.

**Состав:**
- поле поиска `ФИО / Полис ОМС`;
- список пациентов;
- пагинация.

**Логика:**
- поиск выполняется по строке и обновляет список;
- выбор пациента сохраняется в контексте и ведёт на карточку пациента.

**API:** `GET /api/v1/patients`

---

## Экран 8: Карточка пациента у регистратора

**Маршрут:** `/registrar/patient`

**Сценарий:** регистратор видит данные пациента и его активные записи.

**Состав:**
- ФИО и номер полиса;
- список записей;
- кнопки «Удалить» и «Перенести»;
- кнопка «Записать» для перехода к выбору врача.

**Логика:**
- после удаления карточка пациента обновляется;
- при переносе сохраняются выбранный врач и `rescheduleAppointmentId`;
- кнопка «Записать» ведёт к поиску врача.

**API:** `GET /api/v1/patients/{patientId}/dashboard`, `DELETE /api/v1/appointments/{id}`

---

## Экран 9: Поиск врача регистратором

**Маршрут:** `/registrar/doctors`

**Сценарий:** регистратор подбирает врача для выбранного пациента.

**Состав:**
- строка поиска `Имя / Специализация`;
- список врачей;
- отображение выбранного пациента сверху.

**Логика:**
- выбор врача сохраняет его в контексте;
- далее открывается календарь записи.

**API:** `GET /api/v1/doctors`

---

## Экран 10: Календарь регистратура

**Маршрут:** `/registrar/calendar`

**Сценарий:** регистратор создаёт или переносит запись для пациента.

**Состав:**
- календарь месяца;
- список свободных слотов;
- модальное окно подтверждения.

**Логика:**
- если выбран `rescheduleAppointmentId`, выполняется перенос;
- иначе создаётся новая запись для выбранного пациента;
- после успеха пользователь возвращается в карточку пациента.

**API:** `GET /api/v1/doctors/{doctorId}/slots`, `POST /api/v1/appointments`, `PATCH /api/v1/appointments/{id}`

---

## Экран 11: Панель администратора

**Маршрут:** `/admin`

**Сценарий:** администратор управляет пользователями и загружает CSV.

**Состав:**
- поиск пользователей;
- список пользователей с ролью и специальностью;
- кнопка изменения роли и специальности через prompt;
- загрузка CSV для doctors, patients, appointments, work-slots.

**Логика:**
- UI не содержит отдельного экрана отчёта или настройки расписания;
- выгрузка CSV есть на backend, но в текущем frontend не вынесена отдельной кнопкой.

**API:** `GET /api/v1/users`, `PATCH /api/v1/users/{userId}`, `POST /api/v1/admins/import/*`

---

## Навигация и переходы

- после входа пользователь всегда попадает на экран своей роли;
- для возврата между экранами используются кнопки «Назад» и переходы по маршрутам;
- хедер с аватаром содержит только информацию о пользователе и выход из системы;
- отдельного sidebar в текущем UI нет.
