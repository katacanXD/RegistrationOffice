# План доработки хакатонов №1 и №2 (редакция 2)

**Проект:** RegistrationOffice (сервис записи на приём)
**Команда:** 1, ЭФБО-10-25
**Ветка:** `hk_1-3` (от `master`, без merge)
**Дата плана:** 13.11.2026
**Основание:** требования хакатонов, схема преподавателя (`schema.jpg`), методички и раздаточные материалы в `3 семак/`, ревью Kimi, фактический код и документация репозитория.

---

## 0. Что изменилось после правок

1. **Главная опора — методички преподавателя**, а не только ревью Kimi. Документы практических работ делаем по примерам из пояснительных записок к ПЗ 4, 6, 7: та же последовательность шагов, те же таблицы, те же проверки.
2. **Добавлены пять документов практических работ** — это и есть «пояснительные записки» к практикам, а не только заполненные бланки:
   - «Сценарии использования» (ПЗ 3);
   - «Контекст системы» (ПЗ 4, 1–2 страницы);
   - «Контейнеры системы» (ПЗ 5, 2–3 страницы);
   - «Компоненты контейнера» (ПЗ 6, 2–4 страницы);
   - «Модель данных» (ПЗ 7, 2–3 страницы).
3. **Компоненты переработаны по методичке ПЗ 6:** входы, компоненты правил, безопасность, CSV, отчётность, планировщик; **слоя «Доступ к данным» быть не должно** — это слой, а не компонент. Входы не обращаются к БД.
4. **Даты — только прошлое или настоящее.** Все документы пакета v2 датируем `07.11.2026`, исходные версии — `30–31.10.2026`. Никаких будущих дат в документах и плане.
5. **Главная цель — успешная защита.** Добавлен отдельный защитный пакет: демо-сценарий, 12 вопросов-ответов, одностраничник с цифрами, репетиция.
6. **Работаем в ветке `hk_1-3`**, ничего не мержим в `master`.

## 2. Аудит: что подтвердилось

| 2 | ПЗ 3, UC-1 шаг 4: у пациента нет другой записи на это время | Не реализовано: проверяется только слот врача | Реализовать проверку + триггер БД (B3) |

| 4 | ПЗ 3, UC-5: регистратор создаёт карточку пациента | `PatientController` умеет только искать и смотреть | Добавить `POST /api/v1/patients` (B4) |

## 3. Решения

| Вопрос | Решение |
|---|---|
| Стратегия «код ↔ документы» | Гибрид: 5 доработок кода + правки документов |
| Сроки | Без жёсткого срока; последовательно, с приоритетом; **будущие даты не ставим** |
| Команда-оппонент | Есть; согласовать и выдать бланки |
| Формат итоговой ПЗ | Отдельная ПЗ на каждый хакатон |
| `docs/` и README | Синхронизировать полностью |
| Глубина проверки | Статический аудит; для изменённого кода — компиляция и затронутые тесты |
| Отчёт утилизации | Полностью: endpoint + CSV + вкладка в админке |
| ТЗ по ГОСТ 34.602–2020 | Полноценный документ 8–12 страниц |
| UI для причины отмены и создания пациента | Только API; UI не трогаем, ограничение фиксируем в ПЗ |
| «Схема на доске» | Это схема преподавателя; делаем цифровые A3 по ней, фото не нужно |
| Документы практических | Делаем по примерам 4, 6, 7; бланки — приложение |
| Компоненты | 9 компонентов по методичке; без слоя «Доступ к данным» |
| Ветка | `hk_1-3`; без merge в `master` |

## 9. Защита

### 9.1. Одностраничник

- 6 UC, 6 НФТ, 4 контейнера, 9 компонентов, 5 сущностей, 9 процессов DFD.
- Схема «видение → UC → контекст → контейнеры → компоненты → данные → динамика → развёртывание → трассировка».
- Ссылка на репозиторий и демо.
- 5 главных фактов: идемпотентность, запрет пересечения, журнал, создание пациента, отчёт утилизации.

### 9.2. Демо-сценарий (10 минут)

1. Вход пациентом, поиск врача, свободные слоты.
2. Запись на слот; повторный запрос — та же запись (идемпотентность).
3. Попытка записать того же пациента на то же время к другому врачу — 409 (пересечение).
4. Перенос записи; отмена с причиной через API; история операций.
5. Вход регистратором: поиск пациента, создание карточки через API, запись от имени пациента.
6. Вход врачом: расписание на день/неделю, список пациентов.
7. Вход администратором: вкладка «Загрузка», отчёт утилизации, экспорт CSV; импорт CSV.
8. Swagger/curl: показать эндпоинты, которых нет в UI (история, создание пациента, причина отмены).

### 9.3. 12 вопросов-ответов

1. Почему одна таблица `t_users`, а не `patients`/`doctors`? — Роли в `t_dict_role`, меньше дублирования, одна аутентификация; минус — nullable-поля, вынесены в открытые вопросы.
2. Почему статус — атрибут в модели, если есть `t_dict_status`? — Первичная модель логическая; справочник — физическая реализация; правило допустимых значений.
3. Как работает идемпотентность? — Поиск активной записи по врачу и времени; тот же пациент → 200, другой → 409; гонка — unique-триггер.
4. Как запрещены пересечения пациента? — Проверка в сервисе + триггер БД на пару «пациент + время».
5. Где журнал и причина отмены? — `t_appointment_operations`, пишется в той же транзакции; причина — если передана.
6. Почему нет внешних систем? — MVP: без ЕМИАС, SMS, 1С, оплаты; вход и уведомления внутри.
7. Как доставляется SPA? — Отдельный контейнер «Статические файлы» (Nginx + сборка Vite); API не отдаёт статику.
8. Почему не микросервисы? — MVP, малая команда, один процесс; границы компонентов позволяют выделить позже.
9. Что не входит в MVP? — Внешние интеграции, оплата, SMS, отчёт с графиками, UI для причины/создания пациента.
10. Как проверяли? — Юнит/интеграционные тесты, ручные сценарии, Swagger; ограничения фиксируем.
11. Что при одновременной записи? — Триггер с advisory lock; второй запрос получает 409 или идемпотентный ответ.
12. Как считается утилизация? — Сгенерированные слоты за период минус перерывы; занятые — активные записи; CSV по врачу/дате.

### 9.4. Репетиция и резерв

- Прогон 2 раза: 10 минут демо, 5 минут вопросы.
- Резерв: скриншоты, видео, локальный `docker compose`, Postman/curl.
- Проверить, что демо-данные есть (слоты на будущие даты относительно демо; в документах даты не будущие, в демо — можно).

| Рабочий слот | номер слота | дата, начало, конец, длительность, перерыв | Расписание |
| Запись | номер записи | врач, пациент, дата и время, статус | Записи |
| Операция записи | номер операции | тип, актор, время, причина, старое/новое время, старый/новый статус | Записи |
| Токен обновления | номер токена | хэш, пользователь, срок, создан, отозван, заменён | Вход и права |

> Роль и статус — атрибуты с допустимыми значениями (правило курса). Физически — `t_dict_role` и `t_dict_status`; примечание «физическая реализация».

Связи: врач 1:N слоты; врач 1:N записи; пациент 1:N записи; запись 1:N операции; пользователь 1:N операции; пользователь 1:N токены.

Правила:

- **Реализованы:** уникальность логина; допустимые роли; допустимые статусы; уникальность хэша токена; одна активная запись на «врач + время»; одна активная запись на «пациент + время» (B3); обязательные врач/пациент/статус; время в рабочем интервале (сервис).
- **Открытые вопросы:** уникальность полиса; врач ≥1 слот; специальность как справочник; удаление пользователя с записями.

## Приложение Б. Контейнеры и компоненты

**Контейнеры:**

1. «Сайт записи» — React 19, Vite; браузер.
2. «Статические файлы» — Nginx + production-сборка Vite; отдаёт SPA.
3. «API RegistrationOffice» — Java 21, Spring Boot; REST, JWT, правила, CSV, планировщик.
4. «База данных RegistrationOffice» — PostgreSQL 16.

**Компоненты API (9):**

1. «API пациента» — вход для UC-1…UC-3.
2. «API сотрудника» — вход для UC-4…UC-6.
3. «Вход и права» — JWT, роли, вход, refresh-ротация.
4. «Записи» — создание, перенос, отмена, идемпотентность, пересечение, журнал.
5. «Расписание» — рабочие слоты, генерация, календарь.
6. «Пользователи» — пользователи, пациенты, врачи, полис, дашборды.
7. «CSV-обмен» — импорт/экспорт.
8. «Отчётность» — утилизация, CSV.
9. «Очистка токенов» — планировщик, удаляет истёкшие.

**Правила связей:**

- Входы не обращаются к БД; они вызывают «Вход и права» и компоненты правил.
- К БД обращаются «Записи», «Расписание», «Пользователи», «Вход и права».
- «CSV-обмен» вызывает «Записи», «Расписание», «Пользователи».
- «Отчётность» читает через «Расписание» и «Записи».
- «Очистка токенов» вызывает «Вход и права».
- Слоя «Доступ к данным» нет.
